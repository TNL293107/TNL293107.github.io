02 Team capstone · in production

CVerify

AI-powered developer verification platform

Verifies what a developer's CV claims against their actual code — static analysis for complexity, MinHash LSH for clone detection, and Claude for evaluation. A five-person capstone at FPT University, running in production on Google Cloud.

82 commits are mine of 413 on main. The platform is team work; below is the part I owned.

AI service
Built pipelines in the FastAPI microservice — candidate evaluation and JD matching end to end, plus document extraction (PDF/DOCX/image → markdown) and 45 unit tests
Infrastructure
Migrated the deployment runbook from AWS EC2 to GCP Compute Engine, split routing across the app and API subdomains, and got the auto-deploy pipeline actually firing — with daily backups behind it
Observability
Cloud Monitoring alerting on uptime, SSL expiry, CPU, memory and disk — and fixed the Ops Agent config so nginx and container logs actually reached Cloud Logging instead of only syslog
Debugging
Fixed OAuth account linking by scoping the state cookie to the shared domain, and cut a settings page from 22 requests to under the nginx rate limit by collapsing duplicate in-flight GETs

03 Independent

DWatch

Full-stack Java commerce platform

A watch store on plain Servlet/JSP — no framework to hide behind. Cart, COD and VietQR checkout, guest order lookup, wishlist, comparison and an admin console.

  • Migrated stored passwords to BCrypt on first successful login — no user lockouts, no reset email blast
  • CSRF synchroniser tokens across 17 forms; session ID rotation after auth; identical responses for unknown and wrong-password logins
  • 54 JUnit 5 + Mockito tests running fully on mocked DAOs — no database required

04 Independent · v3.4

FU-Autokit

Browser extension for FPT University students

Removes the daily friction of university systems: one credential store, nine portals, and the arithmetic students were doing by hand.

02 — About

Engineering over decoration.

I like problems where the hard part is the data model and the flow, not the screen.

Most of what I build started as something that annoyed me: nine university portals that each wanted the same login, a checkout that could not tell a paid order from an unpaid one, a CV with no way to check whether any of it was true.

The work I enjoy most is the unglamorous half — figuring out why logs never reached the logging backend, why an OAuth callback silently dropped a cookie, why one page fired twenty-two requests to render a single screen. That is usually where a system is actually broken.

I am going deeper into distributed systems, testing and infrastructure, and I am open to backend or full-stack internships.
